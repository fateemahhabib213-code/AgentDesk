# AgentDesk — Architecture

This document explains how AgentDesk's agent loop actually works, for anyone reviewing the internship submission.

---

## 1. High-level flow

```
┌─────────────┐      POST /api/research      ┌──────────────────┐
│  React UI   │ ────────────────────────────▶ │  FastAPI Backend │
│ (Vite+JSX)  │ ◀──── JSON: events + report ── │                  │
└─────────────┘                                └────────┬─────────┘
                                                          │
                                                 ┌────────▼─────────┐
                                                 │  Orchestrator     │
                                                 │  (agent loop)     │
                                                 └───┬───────────┬──┘
                                                     │           │
                                          ┌──────────▼──┐   ┌────▼────────┐
                                          │  Planner /   │   │  Evaluator   │
                                          │  OpenAI calls│   │ (self-correct)│
                                          └──────┬───────┘   └────┬────────┘
                                                 │                │
                                          ┌──────▼──────┐  ┌──────▼────────┐
                                          │ web_search.py│  │ Synthesizer   │
                                          │ (Tavily API) │  │ (final report)│
                                          └──────────────┘  └───────────────┘
```

The frontend never calls OpenAI or Tavily directly — it only ever talks to FastAPI. All reasoning and tool use happens server-side, inside `orchestrator.py`.

---

## 2. Why this counts as an "agent" and not a chatbot

A plain chatbot does:
```
user message → LLM → answer
```

AgentDesk does:
```
goal → plan → search → evaluate → (correct → search → evaluate)* → synthesize → report
```

The difference that matters: **the model itself decides what to search for and whether the results are good enough** — nothing is hardcoded per-topic. The same code path handles "Tesla competitors" and "best productivity apps for students" identically; only the model's output differs. This is what requirement #20 in the original spec ("do not fake agentic behavior") is checking for.

---

## 3. The agent loop, step by step

Implemented in `backend/agent/orchestrator.py`, function `run_agent(goal)`.

### Step 1 — Planning
`planner.create_plan(goal)` sends the goal to OpenAI with a system prompt asking for *one concrete search query*. This replaces a naive `query = goal` with something the model has actually thought about.

### Step 2 — Search
`tools.web_search.web_search(query)` calls Tavily and returns a cleaned list of `{title, url, content, score}` results.

### Step 3 — Evaluation
`evaluator.evaluate_results(goal, results)` asks OpenAI to judge the results against the original goal and return **structured JSON**:
```json
{ "quality": "high" | "medium" | "low", "reason": "..." }
```
Structured output (rather than free text) is what lets the orchestrator make a real `if` decision on the result, instead of guessing from prose.

### Step 4 — Self-correction (the core requirement)
If quality is `"low"`:
1. The reason is recorded.
2. `planner.refine_query(goal, previous_query, reason)` asks OpenAI for a *better* query, given what went wrong.
3. The loop goes back to Step 2 with the new query.
4. This repeats until quality is acceptable **or** `MAX_RETRIES` is hit.

```python
attempt = 0
while attempt <= MAX_RETRIES:
    results = web_search(query)
    verdict = evaluate_results(goal, results)

    if verdict["quality"] in ("high", "medium"):
        break                      # good enough, stop

    if attempt == MAX_RETRIES:
        break                      # out of retries, proceed anyway

    query = refine_query(goal, query, verdict["reason"])
    attempt += 1
```

`MAX_RETRIES` (default `2`, set in `.env`) guarantees the loop is bounded — it can search at most `MAX_RETRIES + 1` times before giving up and moving on with whatever it has. This is a hard safety limit, not a suggestion to the model.

### Step 5 — Synthesis
`synthesizer.synthesize_report(goal, results)` takes whatever results the loop ended with (even if quality was never great) and asks OpenAI to write a structured report — again as JSON, not free text, so the frontend can render each section (`executive_summary`, `key_findings`, `comparison`, `conclusion`) predictably. Sources are attached from the orchestrator's own result list, **not** generated by the model, so links can never be hallucinated.

## 4. Agent state

Every step appends a structured event to an `events` list:
```json
{ "type": "evaluation", "status": "completed", "verdict": { "quality": "low", "reason": "..." } }
```

This list *is* the agent's state and audit trail. It's returned in full to the frontend, which uses it for:
- The **Live Agent Activity** timeline (every step, in order)
- The **self-correction visualization** (paired `correction` "started"/"completed" events showing previous → refined query)
- The **progress stepper** (derived by checking which event types are present)

Event types: `goal_received`, `planning`, `search`, `search_results`, `evaluation`, `correction`, `synthesis`, `completed`, `error`.

---

## 5. Error handling

Each stage of the loop (planning, search, evaluation, correction, synthesis) is wrapped in its own `try/except`. If one stage fails:
- An `error` event is logged with the stage name and message.
- The loop breaks out of that stage gracefully and proceeds with whatever it has, rather than crashing the whole request.
- The outer `/api/research` route also has a catch-all, so a total failure still returns a JSON error instead of a 500 with no explanation.

This is "graceful degradation": one failed piece doesn't take down the whole response.

---

## 6. Known limitation: no streaming yet

The backend currently returns one JSON response after the *entire* loop finishes — it does not stream events via Server-Sent Events as they happen. This means the frontend's "live" activity feed is populated all at once on response, not incrementally while the agent works. The architecture already supports adding SSE later (the `events` list is built incrementally inside `run_agent`; it would just need to `yield` instead of `append` and be wired to a streaming FastAPI response) — it was left out to prioritize a working end-to-end loop over transport complexity, per the project's own "working project > complex architecture" rule.

---

## 7. Frontend structure

- `App.jsx` — top-level state (`goal`, `events`, `report`, `loading`, `error`) and the single `fetch("/api/research")` call.
- `ChatView.jsx` — renders the submitted goal as a user message and the agent's progress/report as an agent message, chat-style.
- `ResearchProgress.jsx` — derives stage completion (Plan/Search/Evaluate/Refine/Synthesize) and self-correction blocks purely from the `events` array — no separate state needed.
- `AgentActivity.jsx` — maps each raw event to a human-readable label/detail/status for the sidebar timeline.
- `ResearchReport.jsx` / `SourceCard.jsx` — render the final `report` object.

All of these are pure functions of the data FastAPI returns — no component invents data that didn't come from the backend.
